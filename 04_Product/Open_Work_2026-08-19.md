## 1. Buildable now, no founder input needed

### 1.1 The streak is roughly right; the app never SHOWS which Steps bind — DONE (2026-08-19)
**Refined by the founder, 2026-08-19, and this supersedes his first framing an hour earlier.**

He first said a streak day should mean "I did all of today's Steps". On reflection he corrected
himself, and the corrected version is the one to build:

> *"אם משימה לא מחויבת ליום מסוים היא יכולה גם להופיע למחרת וזה בסדר — זה לא צריך לשבור את ה־streak.
> הבעיה לדעתי שויזואלית זה נראה באפליקציה … צריך שיופיע חיווי של recommended, ואז אי ביצוע שלו לא
> שובר את ה־streak."*

So the shipped LOGIC is close to correct. A workout that could happen Wednesday *or* Thursday
carries slack, and missing it on Wednesday is not a failure — exactly what
`app/src/core/config/streak.ts` (D26.4) already encodes: only a Step with **no slack left in the
week** breaks the streak.

**The actual defect is that the user cannot see the difference.** Two Steps render identically on
Home. He missed one, his streak rose, and nothing on screen explained why — which is why it read as
a bug. A rule the user cannot see is a rule the user cannot trust.

**What to build — a VISUAL distinction, not a new rule:**
- A Step **with slack** is marked **`recommended`** (his word). Missing it never touches the streak,
  and the label is what says so before the fact rather than after.
- A Step with **no slack left** is the binding one: doing it today is what holds the week together,
  and missing it is what breaks the streak.
- The engine already computes this (the urgency test behind `STREAK_CONFIG`), so this is surfacing
  an existing derivation, not inventing one. Do NOT fork a second definition in the UI — read the
  same one, the way `core/util/milestones.ts` is shared.

**Do not change D26.4's rule.** The founder has now confirmed it twice over; what was missing was
ever telling him about it.

**Copy warning:** `recommended` must never read as optional-and-therefore-unimportant, and the
binding state must never read as a threat. This is the app that promises no penalty for a life that
got in the way — the difference being shown is about the WEEK's arithmetic, not about the user.

### 1.3 The shared completion image loses the whole design — ANSWERED, awaiting the founder
**The most visible of these — it is what the partner will see.** The completion card is designed
and looks right on screen; tapping Share sends plain text ("You did it / Build core strength") with
none of it. It must share as an IMAGE identical to what was shown. Needs a view-to-image capture.
Check first whether that is possible without a new native dependency; if it is not, say so and let
the founder decide before adding one.

**Answer (2026-08-19): it is NOT possible with what is installed.** Nothing in the current dependency
set can rasterize an arbitrary React Native view. `react-native-svg` is present and can export ITSELF
to an image, but the card is Ionicons glyphs, theme tokens and custom fonts — re-authoring it as SVG
would duplicate the design and gamble on fidelity, which is the opposite of "identical to what was
shown". A faithful capture needs `react-native-view-shot` (MIT, free, no metered service, no recurring
cost). It is a NATIVE dependency, so it must land before the single partner build — the same build
sign-in already requires. The seam is already built and unchanged (`core/share/`, whose own header
names this exact package): saying yes replaces the Null gateway with one file and moves no caller.
