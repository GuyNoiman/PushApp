# Device QA — first native build, 2026-08-17

Status: **Open findings.** The founder's first pass on a real iPhone, against the first EAS
development build (`com.guynoiman.pushapp`). Everything below was found on device; none of it was
caught by 1442 passing tests, which is the point of the exercise.

Ordered by kind: real defects first, then design decisions the founder made while testing, then
things needing a product call.

---

## A. Defects

### A1. "Milestone N of M" has two different sources, and one of them is invented
**Confirmed in code.** Home (`app/src/app/(tabs)/index.tsx:103`, `milestonePosition`) reads the
**real** `journey.milestones` and reports `m.order + 1` of `milestones.length`. The Journeys tab
(`app/src/components/journey/journeyView.ts:102`) instead computes
`phases = Math.max(1, Math.min(4, totalSteps || 1))` and the card labels it "Milestone X of Y".

So the same Journey showed **Milestone 1 of 3** on Home and **Milestone 1 of 4** on Journeys. The 4 is
not a Milestone count at all — it is a capped Step count wearing a Milestone's label.

The founder's own reaction is the correct diagnosis: *"I never saw or approved any Milestone."* On the
Journeys surface there were none to see.

**Fix:** `journeyView` must read real Milestones. Where a Journey genuinely has none, say nothing
rather than inventing a number. Note the field is named `phase`/`phases` in the view model, a leftover
of the superseded "Phase" terminology — renaming it is part of the fix.

### A2. Progress reads 0% after a Step was reported done
Reported via swipe-to-done on Home; the Journeys card still showed 0%. `progress = doneSteps /
totalSteps`, so one done Step out of ~8 should read 12%, not 0. Needs investigation: whether the
report persisted, whether the card re-read the snapshot, or whether rounding floors it.

### A3. The keyboard covers the field being typed into
Two places, same cause:
- **Onboarding, birth date** — the field does not centre and the page does not scroll, so the field
  the user is typing into is behind the keyboard.
- **Active Hours, per-day setup** — the last row (Saturday) is hidden the same way.

This is a general screen-level defect, not two separate ones. Any scrollable form with inputs near the
bottom will have it.

### A4. A new Journey was given an unrelated name
The founder asked for "drink a protein shake daily". The Journey was created with a Hebrew title but
its Steps were a generic wellness template — *move at a comfortable pace*, *stretch or wind down*,
*eat your meals at roughly regular times*. Nothing about a protein shake.

### A5. A Journey asked for one daily action produced many Steps
Same case as A4. "This week" filled with Steps the user never asked for.

### A6. Odd visual state on a completed Step
After swiping a Step to done, the completed row renders oddly. Screenshot pending from the founder.

### A7. The Support Circle panel shows a load error on a fresh install
Visible in the Journey detail screenshot: *"Couldn't load your Support Circle. Try again."* Expected
when the social pillar has no session, but a first-run user should not meet an error banner. This is
the offline-load-vs-genuinely-empty distinction that was hardened earlier — it may be reporting the
wrong one here.

## B. Decisions the founder made while testing

### B1. Home first, not the Coach
On sign-in the Coach opens immediately. **Decision: land on Home.** The Coach stays one tap away via
the hero card.

### B2. The initial state must be clean
A fresh install already has Journeys and Steps before the user has set anything up — the demo seed
(`AppCore.seedDemoJourney`). **Decision: first run must be empty.**

Consequence to think through rather than just delete: several surfaces have only ever been seen with
seeded data. Removing it exposes every empty state at once, which is a good thing to face now.

### B3. The ⋯ menu is in the wrong place
On the Journey detail screen it floats below the actions. **Decision: move it to the top bar, next to
the edit button.**

This supersedes part of today's earlier change, which deliberately put Cancel and Delete at the *end*
of the action list under an overflow control. The de-emphasis intent stands; the placement does not.

---

## C. Needs a product decision

### C1. Birth date should be a picker, not typed
The founder expects a calendar/wheel picker rather than typing a date, and is right that typing a date
is dated. Note the constraint that shaped the current control: **no new native dependency**, so the
app keeps working in Expo Go and the web preview. A date picker built from existing primitives is
possible; a native one is not, without revisiting that rule.
