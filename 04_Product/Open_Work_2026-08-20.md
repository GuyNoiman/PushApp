## 3. Standing context — read before touching anything native

### 3.1 The fingerprint rule
The partner's build carries iOS runtime fingerprint **`df6c2127bbd3be3766774e3f008f4ae5158306cd`**.
Updates only reach a binary whose fingerprint MATCHES. **A native dependency, any `app.json` edit, or
an SDK bump changes it and cuts his phone off from every update we publish.** Not native, and
therefore free: all TypeScript, every component, i18n copy, colours, artwork drawn in code, and fonts
(loaded at runtime from JS assets — verified: adding two font families left the hash untouched).
`expo-blur` and `expo-linear-gradient` were added BEFORE the build precisely so the redesign would
never need one. If a native change becomes genuinely necessary, it means a new build and the partner
has to install it: raise it, never do it as a side effect.

### 3.2 A DEV RUNTIME OLDER THAN THE DEPENDENCIES CANNOT RENDER THEM
`Unimplemented component: ViewManagerAdapter_ExpoLinearGradient` on three screens (the Coach card,
the week's summary, the Tools hero) means the app binary on the device predates 2026-08-19 15:21,
when `expo-linear-gradient` and `expo-blur` were installed. It is not a code bug and **no graceful
fallback was built for it on purpose**: the only available check (`UIManager.getViewManagerConfig`)
is unreliable under the New Architecture, and a wrong answer would flatten the redesign in real
builds. The fix is the runtime — Expo Go bundles the module at no cost, or a fresh development build.

Related: `npm run dev` publishes the packager under `scutil --get LocalHostName`, a `.local` mDNS name
iOS often cannot resolve, which makes a saved Expo Go entry hang with no error. Start with
`REACT_NATIVE_PACKAGER_HOSTNAME=<LAN IP>` and verify the manifest's `launchAsset.url` carries the IP.

### 3.3 The tab bar exists twice
`app-tabs.tsx` (native) and `app-tabs.web.tsx` (web) are separate files kept in sync BY HAND. A tab
added, removed or renamed in one is invisible in the other. This cost an hour on 2026-08-20.

### 3.4 Nobody's name in shipped copy
`src/i18n/__tests__/noPersonalData.test.ts` sweeps every resource file for development identities and
fails if one ships. It exists because the coach's greeting said "Hi Guy" to every user, in both
languages, for months. Add a name to that blocklist when a new person works on the app; never add a
user's data to it.

### 3.5 A release build cannot invent data
The demo seed and the simulated identity are gated on `__DEV__` as well as on their env vars
(`core/config/featureFlags.ts`, `core/profile/simulatedUser.ts`), so a shipped app cannot seed
Journeys or show a developer's name however the environment is configured.
`src/core/__tests__/cleanFirstRun.test.ts` holds that down.
