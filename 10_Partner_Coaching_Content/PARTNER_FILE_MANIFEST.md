# Partner Coaching Content — File Manifest

Status: **Living manifest.** Generated 2026-08-13 from `PushApp_Guy_Content_Evaluation_v1.1.zip`.

## What this is

Every file listed below was authored by the **external coaching partner**, not by the PushApp team.
They are tracked separately so the founder can remove the entire package in one action if the
partnership does not proceed.

**Rules for this folder (founder decision, 2026-08-13):**

1. These files may be edited **for terminology alignment only**, so they read correctly against
   `09_Product_Philosophy/Product_Terminology.md`.
2. **PushApp's own code must NOT be changed to accommodate this content without the founder's
   explicit approval.**
3. Nothing here is wired into the app. It is reference content pending evaluation.

## Removing the whole package

```bash
git rm -r 10_Partner_Coaching_Content && rm -f 10_Partner_Coaching_Content/PARTNER_FILE_MANIFEST.md
```

No other directory in this repository contains partner-authored files, so that single command is
sufficient. If any partner text is later copied into our own docs or code, it must be recorded
in the "Derived work" section at the bottom of this file.

## Terminology-alignment pass — 2026-08-13

Applied under rule 1 above, to 12 of these files. The eating-mechanism headings `Step A–E` became
`Stage A–E`, because `Step` is our smallest unit of progress and the same section already uses it
in that sense. The heading `Arc` became `Milestones` in 60 places across 9 files, since the package
itself heads identical content `## Milestones`. Three generic uses of `Ally` were widened so a user
in an addiction crisis is also pointed at a sponsor, clinician or family member, who are not Allies.
Nothing else was touched. Around 515 other candidate edits were deliberately left alone so the
coaching prose and its cited academic sources stay accurate.

**Language exception:** `11_GUY_UPDATE_HE.md` is written in Hebrew. Repository language is English
(`CLAUDE.md` §3.7), but this file is verbatim partner correspondence rather than a PushApp document,
so it is kept exactly as received, not translated and not rewritten.

## Second terminology-alignment pass — 2026-08-14

Applied under rule 1 above, to **27 of these files**, after the founder ratified two naming decisions
(**Decision Log D48 and D49**). 164 replacements in total. The file table above was regenerated after
this pass, so every size and hash reflects the edited state.

**`Meta-Coach` → our coach naming — 111 occurrences.** The partner's Meta-Coach is the same entity we
call **the coach**, whose architectural name is **meta-agent** (D30, D49). Each occurrence was read
before it was changed: **"the coach"** where the sentence is about what the user experiences (identity
lists, "user-facing voice", what the coach says or must not say, the wording of safety tables), and
**"meta-agent"** where it is architecture (spec metadata, Dream ownership, Expert consultation, on-call
hand-back to the orchestrating layer). All casings the package used were covered — `Meta-Coach` (72
outside the two files noted below), plus `meta-coach`, `Meta-coach`, `META-COACH` and `Meta Coach`.

**Filenames were deliberately left unchanged.** `Master_Specs_Original/15_Meta_Coach_Master_Spec.md` and
`Calibration/14_Meta_Coach_Calibration_24_Cases.md` keep the names the partner sent, so the package stays
traceable to the original zip. Their *contents* use our naming, and the in-content cross-reference to
`` `14_Meta_Coach_Calibration_24_Cases.md` `` was left as-is because it is a filename, not a term. This
mismatch between filename and content is intentional.

**`intervention` → `comment`, reactive sense only — 53 occurrences.** Our `intervention` is a
**proactive** action PushApp initiates; the partner's was the opposite, a **reactive** coaching move
inside a conversation the user started. Founder decision (D48): ours keeps the word, theirs becomes
**`comment`**. `Prepared intervention` → `Prepared comment`; `Level 1 — Prepared micro-intervention` →
`Level 1 — One prepared comment` (the "micro-" prefix was dropped rather than coining "micro-comment" —
a comment is already the small unit); sentences were re-read and adjusted so each still reads naturally.

**45 academic/clinical uses of `intervention` were deliberately not touched** — "intervention research",
"behaviour-change interventions", NICE guidance and the meta-analysis citations (Masi, Liu/Huang/Wang,
Guest, Alleva, Oprea, CDC). Renaming those would misrepresent cited sources.

**Four occurrences were left alone as genuinely ambiguous**, rather than guessed at:

1. `01_Eating_Daily_Consistency_Progression.md` §11 — "A measurement tool that worsens rigidity is not a
   successful intervention." Reads as a clinical judgement about the tracking mechanism, not a
   conversational move.
2. `02_Body_Image_Master_v1.1.md` §6.2 (and its near-duplicate `Master_Specs_Original/26_…`) — the
   heading "Observation before intervention". The same phrase appears as a cited principle in
   `Research/21_…` §"observation before intervention", so changing the heading would split it from its
   source.
3. `Calibration/14_…` Case 11 — "motivation as if it were a consumable intervention." "Consumable
   comment" would not carry the meaning.
4. `Calibration/14_…` Case 18 — "Continued intervention can undermine autonomy." The case is about a
   user who no longer needs frequent **prompts**, so this one arguably reads correctly in *our* proactive
   sense already.

**Duplicate handling.** Every edit was mirrored into the concatenated
`10_PushApp_v1.1_COMPLETE_QUALITY_EVALUATION.md`. Verified afterwards: the two exact-duplicate pairs
(`03_…` = `Journeys/22_…_v1.1`, `04_…` = `Calibration/25_…_21_Cases_v1.1`) still hash identically, the
three near-duplicate pairs (`02|05|06` vs `Master_Specs_Original/26|32|38`) carry identical terminology,
and all 81 edited lines in the bundled source files are present verbatim in the consolidated bundle.

**Nothing else was touched** — no coaching content, sequencing or clinical judgement was altered, and no
PushApp code was changed to accommodate this package.

## Model differences with our own product — resolved, 2026-08-13

Two places where this package's model differs from PushApp's own were flagged during the terminology
audit above and have since been resolved by the founder (Decision Log **D47**):

- **Ally.** The partner content used "Ally/support" loosely enough to also mean a sponsor, a clinician,
  or a family member (the widening noted in the terminology-alignment pass above). **Resolved in our
  favour:** an Ally is only ever someone the user chose to add to a Journey's Support Circle — nothing
  else. Real-world supporters are not Allies and are not currently modeled as any in-app concept; the
  coach must refer to them in plain language and must never route a user to the in-app Ally list as if
  it were crisis support. Whether real-world supporters should ever become their own modeled concept is
  left open. See `09_Product_Philosophy/Product_Terminology.md` (Ally entry) and `06_Decisions/
  Decision_Log.md` D47.
- **Dream ownership.** The partner content's Meta-Coach spec treats Dreams as an internal-only
  abstraction the coach owns and the user never directly sees. **Resolved as: our Dream stays
  user-visible** — the Dreams screen stays visible for now, because it helps testing. The founder noted
  this may be hidden later; the decision is explicitly marked revisitable, not final. See
  `06_Decisions/Decision_Log.md` D47.
- **Weekly Review** *(added 2026-08-14, Decision Log **D50**)*. `01_Eating_Daily_Consistency_Progression.md`
  §7 describes a per-Journey weekly `STABILIZE / ADAPT / PROGRESS` adherence review. **Resolved: it is not
  a second object.** There is exactly **one** Weekly Review — ours (`04_Product/PRD/Done/Weekly_Review_PRD.md`,
  D40/D43) — and the founder's framing is that it is a **shared mechanism available to every domain expert
  and every Journey, into which they can contribute information for display**. A per-Journey review like
  this one becomes nested content inside that single weekly surface. The partner's text was **not edited**
  for this; it is an architectural resolution, and it depends on a **contribution slot that does not exist
  in the code yet** (a future implementation item, not built today).
